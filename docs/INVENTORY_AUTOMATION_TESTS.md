# ERP Inventory Automated Test Coverage

## Purpose

Continuous automated test coverage for the ERP Inventory module (this frontend, `OneSphere-Inventory`, plus the Inventory-related controllers/procedures in the `GLOBAL_ACCOUNTS_LATEST` backend). Updated whenever Inventory test coverage meaningfully changes — reflects current state, not a chronological log.

## Testing Stack

- **Frontend test runner**: Angular's native `@angular/build:unit-test` builder (Vitest-backed — see `angular.json`'s `test` target and `vitest` in `package.json`). No Karma/Jasmine in this repo. Run via `ng test` or `ng test --include='<glob>'` to scope to one spec.
  - **Fixed 2026-08-14**: the `test` target had no `buildTarget` configured, so it defaulted to the project's federation `build` target (`@angular-architects/native-federation:build`), which the unit-test builder doesn't support — every `ng test` run failed with `pluginOptions.instrumentForCoverage is not a function`, including on the two pre-existing spec files. Fix: pointed `test.options.buildTarget` at the already-existing `esbuild` target (plain `@angular/build:application`, the same one `serve`'s underlying config already resolves through) — see `angular.json`. Verified: pre-existing specs and the new one below all pass now.
- **Frontend component testing**: `TestBed.configureTestingModule({ imports: [StandaloneComponent], providers: [...] })` + `ComponentFixture`, standard Angular signals-based component testing. Spec files are `*.spec.ts`, colocated next to the component/module they cover. For a component with `@Input({ required: true })`, set the input directly on the fixture's component instance before `detectChanges()`. Private business-rule methods are reachable via `(component as any).methodName(...)` when going through the full async/UI path would be disproportionate to what's being verified — see the reference-picker spec below for the pattern.
- **Backend**: xUnit + Moq (`Kapil_Group_ERP_API.Tests`), controller-layer tests against mocked services via shared helpers in `TestSupport/` (`ControllerTestContext`, `TenantContextFactory`, `TestableControllerBase`, `LoggerMockExtensions`). Run via `dotnet test --filter "FullyQualifiedName~<ClassName>"` from `Kapil_Group_ERP_API.Tests/`, or `dotnet test` for the whole project.
  - **Fixed 2026-08-14**: the whole test project failed to *compile* because `Controllers/UsersControllerTests.cs` (Users/Accounts module, not Inventory) called `IMultiTenantDataService.CreateUserAsync(...)`, a method removed when production code moved to an `InviteUserAsync`-based invite flow — see `erp_multitenant_architecture` project memory. Beyond the rename, `UsersController.Create` now returns a plain 200 OK ("Invitation sent") instead of `201 CreatedAtAction` pointing at `GetById`, since no users row/id exists yet for an invitation — the stale test asserted the old `CreatedAtActionResult` shape, so that assertion was rewritten to match, not just renamed. This is outside the "Inventory only" scope in isolation, but it was blocking every backend test in the project (Inventory included) from running at all, so it was fixed rather than left broken.
  - **Fixed 2026-08-18**: the whole test project again failed to compile — `Controllers/InventoryTransactionsControllerTests.cs` called `InventoryTransactionsController`'s 4-arg constructor, but the controller had since gained a required 5th `S3UploadService` parameter (Purchase Invoice Attachments, `147_purchase_invoice_attachments.sql`) that this test file was never updated for. Fixed by building a real `S3UploadService` over mocked `IAmazonS3`/`ILogger` + the existing in-memory `IConfiguration` (`S3ConfigRepository` only needs `IConfiguration` to construct, no DB call at construction time) — none of the tests in that file exercise upload/download, so a real-but-unused instance is enough. - **Backend SQL/stored-procedure logic**: no automated test layer exists for this yet — business logic in `Database/Migrations/inventory/*.sql` (stock posting, reference-picker exclusions, report aggregation, etc.) is currently verified only by manual `psql` checks against the live/shared database, not by an automated suite.

## Business Rules Covered

- Inventory Audit Trail report's route-driven definition lookup and preview-vs-API-data state.
- **DC reference-picker exclusions** (regression coverage for this session's circular-reference fix):
  - An SO already referenced by an existing, non-cancelled DC (even a draft one) is excluded from being offered again — matched by both `so_id` and `so_number`.
  - An SO whose only referencing DC was cancelled is *not* excluded (cancellation doesn't count as "used").
  - An SI item already consumed by an existing DC is excluded at the item level, leaving the rest of that SI doc's other items available; the whole SI doc drops out only once every item is used.
  - All of the above is a no-op when `config.key !== 'deliveryChallan'` (doesn't leak into SI/other screens).
- **Debit Note / Credit Note Invoice reference (item 18)** — Debit Note's and Credit Note's Settlement Reference dropdown/tray now merges two doc types (mirrors Sales Invoice's existing SO+DC merge): Purchase/Sales Return docs (unchanged) plus posted Purchase/Sales Invoice docs (new — backend columns `purchase_invoice_id`/`purchase_invoice_number` and `sales_invoice_id`/`sales_invoice_number` already existed in migrations 051/054 and were already read/written by `sp_upsert_debit_note`/`sp_upsert_credit_note`; only the frontend reference-picker wiring was missing).
  - Picking an Invoice doc routes through `selectPurchaseReference`/`selectSalesReference`, branching on `referenceDocType(doc)` to populate `purchaseInvoiceId`/`purchaseInvoiceReference` (or the sales equivalents) instead of `purchaseReturnId`/`salesReturnId`, and seeds settlement lines from the invoice's own items, labelled "Purchase Invoice"/"Sales Invoice" instead of "...Return".
  - The "already used, don't offer again" exclusion (`filterDocumentNoteAvailableReturnDocs`) applies only to Return-type docs — an Invoice can legitimately be referenced by more than one Debit/Credit Note over time (e.g. separate partial price adjustments), so it is never excluded once referenced. Deliberate, documented decision (see the method's own comment and the spec file's header comment).
  - `buildPayload()` now gates `purchase_return_number`/`purchase_invoice_number` (and the sales equivalents) on their own id actually being set, instead of always echoing the dropdown's display label into `purchase_return_number` regardless of which doc type was picked — this also fixed a latent mislabelling bug where a Direct entry's literal "Direct Debit Note" text was being written into `purchase_return_number` in the DB.
  - Reload (`applyPurchaseRecordToForm`/`applySalesRecordToForm`) now falls back to the invoice number when the return number is absent, so an Invoice-sourced note shows its real reference again after a page reload instead of a blank field.
- **Shared mode-of-payment component (item 19)** — new `app-payment-mode-selector` (`src/app/shared/payment-mode-selector/`), cloned UX-only from OneSphere-Accounts' General Receipt screen (`general-receipt-new.ts`/`.html`) and duplicated byte-for-byte into both `OneSphere-Inventory/src/app/shared` and `OneSphere-Accounts/src/app/shared` (same precedent as `shared/login`/`shared/main-layout`), zero dependency on either app's own services/directives so the copy is genuinely drop-in.
  - Top toggle Cash/Bank; Bank reveals a Cheque/Online/Debit Card/Credit Card sub-tab row; Online reveals a nested UPI field when its "Type Of Payment" is UPI. Field sets, required-ness, and show/hide rules mirror the live Accounts screen field-for-field.
  - Two deliberate adaptations (not silent invention — both because Inventory has no backend for this data today): "Bank Name"/"Deposited Bank Name" render as an `ng-select` when the caller supplies a `banks`/`depositBanks` list, else fall back to free text in the same slot; "Type Of Payment" defaults to a static NEFT/RTGS/IMPS/UPI list instead of Accounts' DB-driven list, overridable via `onlinePaymentTypes`.
  - Wired into `payment-receipt-voucher.ts`/`.html` (Vendor Payment + Customer Receipt), replacing the screen's old ad-hoc `MODE_DEFS` dropdown-plus-generic-text-fields. `ModeRow` now pairs an amount with the selector's full output (`{ details: PaymentModeSelectorValue; amount }`); `buildRefJson()` flattens that into the flat string map `inv_payment_voucher_modes.ref_json` already expects, with `modeKey` staying exactly `'cash'` for Cash (verified against `093_category_ledger_posting.sql`, which branches `IF v_mode_key = 'cash'` to route CASH ON HAND vs BANK — no backend/schema change needed or made).
  - `save()` now blocks and calls `markAllTouched()` on every active row's selector when a mode row with `amount > 0` isn't valid per the selector's own field rules, mirroring Accounts' own save-time validation gate.
- **GRN/PI grid-header "Add Product" → real routed navigation (item 26)** — GRN's and PI's line-item grid header gained a new `addProductFromProcurementGrid()` trigger (a plain button, "Add Product", next to the existing "Add Row"/"Full Screen" buttons in `goods-receipt.html`/`purchase-invoice.html`) that does a genuine `Router.navigate()` to the real Product/Service Master screen (`/dashboard/inventory/masters/product-service-master`), instead of opening the lightweight `InventoryQuickAddModalComponent` used by every other field's "+" (Vendor, Customer, UOM, other product pickers) — those are completely untouched by this item.
  - In-progress GRN/PI state is preserved via a one-shot `sessionStorage` snapshot (`inv_procurement_resume::<screenKey>`, TTL 30 min) taken immediately before navigating away, keyed off `formValues`/`entryLineRows`/`editingId`/`txDocId` and the various line-level maps (attribute/serial/ref-item/serial-units/GST-included) and Transport Details. This is deliberately **not** routed through the existing "Save Draft" DB flow — GRN/PI's Draft validation (`validateGrnLineItems()`) unconditionally requires a product already selected on every line, which is exactly not true at the moment this button is needed (the product doesn't exist yet), so a forced Draft save would routinely fail validation and block the feature.
  - The navigation carries `?returnTo=<goodsReceipt|purchaseInvoice>&returnRoute=<path>` as query params. Product Master's own save success handler (`navigateBackAfterProductMasterSave()`, called from the shared `finishSave()` inside `executeSaveConfigRecord()`) reads those params and navigates back with `?resumed=1` **only when `config.key === 'productServiceMaster'` and both params are present** — a normal, unrelated visit to Product Master (no query params) never navigates anywhere, leaving standalone usage byte-for-byte unaffected. A failed product save also never navigates back.
  - Back on GRN/PI, `restoreProcurementResumeIfReturning()` (called at the top of `ngOnInit()`, before `directEntryLineRows()`/other init logic can stomp `entryLineRows` back to a blank row) restores the snapshot only when the URL actually carries `?resumed=1`, then deletes the one-shot key. A plain/unrelated visit to GRN or PI — even with a stale leftover snapshot sitting in `sessionStorage` from an abandoned detour — never auto-applies it. An expired (>30 min) snapshot is discarded instead of restored.

## Live-Verification Findings (Stock Valuation Comparison Report, 2026-08-18)

- **Found and fixed as a side effect of a routine restart, not a new migration**: while creating test cost layers to verify this report, `fn_post_pi_stock` (guarded, `123`/`124`/`139`) was live-reverted to a pre-139 body with no `fn_add_stock_cost_layer` call — new Purchase Invoice posts across the *entire* system were silently creating stock without a cost layer. `inventory.tbl_guarded_function_defs`'s own stored snapshot for `fn_post_pi_stock` had been overwritten with the bad (no-layer-call) body at 2026-08-18 11:49:17, hours before this session touched anything — consistent with the `erp_migration_restart_race` gotcha (a second, racing `dotnet run` re-applying 139's guard-bypass sequence concurrently with another). A single clean restart (all `dotnet.exe`/orphaned `Kapil_Group_ERP_API.exe` killed first, exactly one instance relaunched) let migration 139 re-apply cleanly and self-heal both the function body and the guard's snapshot — confirmed stable across 3 checks ~6s apart. No new migration was needed; this is a live-state fact, not a code fix, so nothing here re-guards or re-registers anything already covered by 139. Flagged for awareness: any Purchase Invoice posted between whenever the bad snapshot landed and this restart has stock quantity with no matching cost layer (falls back to the product's `cost_price` at next consumption, per the engine's existing shortfall behavior — never blocks, just less precise for that lot).
- **Found, then fixed same day (2026-08-18)**: `app-bar-chart`/`app-line-chart`/`app-donut-chart` initially rendered a blank canvas in the real federated app — `provideCharts(withDefaultRegisterables())` registered in `OneSphere-Inventory/src/app/app.config.ts` never actually takes effect through native federation (Inventory is loaded as a remote into `OneSphere-Accounts`' host shell, which provides its own root injector — same "two copies, only the host's is live" shape as the CSS/main-layout gotcha, see `erp_inventory_accounts_shared_css_duplication`, but for DI providers instead of CSS). Confirmed live: the Dashboard's own charts were equally blank (`"category" is not a registered scale"` in the console). **Fixed** by adding a module-level `Chart.register(...)` side-effect call at the top of `Inventory_Shared/charts/chart-palette.ts` (imported by every chart wrapper) instead of relying on Angular DI — a plain ES module top-level call always executes once on import regardless of which app's injector loaded the component tree, so it sidesteps the federation-DI-scoping gap entirely. `provideCharts(...)` was left in `app.config.ts` too (harmless, and it's what `TestBed`-based unit tests actually exercise). Verified live: canvas count went from 0 to a real rendered count on both the Stock Valuation Comparison report and the MIS Report, with genuinely different bar heights matching the underlying figures. See project memory `erp_federation_di_providers_dead`.
- **Verification-methodology lesson from the above**: the bug was invisible to earlier live checks because every chart wrapper's `hasData()` guard skips instantiating Chart.js entirely when a series is all-zero/empty — so testing only against a data-sparse test company can pass every "does it render" check while the actual chart-instantiation code path goes completely unexercised. Any future chart verification needs genuinely non-empty series data, not just a clean empty state.

## Testing Conventions

- Match the existing `*.audit.spec.ts` / `*.registry.spec.ts` pattern: one spec colocated next to the file it tests, `describe`/`it`, real component imports (standalone), minimal provider mocking (`HttpClient`, `MessageService`, `ActivatedRoute` route params as needed).
- Backend: one `<Controller>Tests.cs` per controller under `Kapil_Group_ERP_API.Tests/Controllers/`, built on `TestableControllerBase`/`ControllerTestContext` from `TestSupport/`.
- Scope strictly to Inventory — do not add tests for Accounts/HRMS modules from here.
