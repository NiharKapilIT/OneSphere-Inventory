# Stock Movement and Manufacturing

Author's note: traced directly against the live frontend config (`inventory-screen.model.ts`), the shared screen shell (`inventory-screen-shell.ts`), the C# data service (`InventoryTransactionsDataService.cs`), and the Postgres migrations under `Database\Migrations\inventory\` (139 through 174) — not from a spec. Where the code and the marketing copy in a screen's own `outputImpact`/`subtitle` disagree, that's called out explicitly.

## Part 1 — Stock Movement: narrative

Before any purchase, sale or transfer can be posted, the stock ledger needs a starting point. That's what **Opening Stock Entry** is for: it seeds `inventory.inv_stock_balance` with a warehouse-wise quantity and, critically, a real cost layer in `inventory.inv_stock_cost_layers` at the rate the user enters — closing the "historical stock has no layer" gap the FIFO/LIFO/Weighted-Average valuation engine (migration 139) would otherwise fall into. There is a second, similarly-named screen, **Opening Inventory Balance**, that looks like it does the same job (same subtitle intent, same fields) but is a completely separate, unwired master-data screen with no table, no save endpoint and no posting function behind it at all — confirmed directly in the shell's own code comments (see its section below). In practice Opening Stock Entry is the real one; Opening Inventory Balance is dead weight that should either be wired up or removed.

Once live operations are running, **Stock Transfer** and **Stock Adjustment** are the two ways stock moves or corrects outside the buy/sell cycle. Stock Transfer moves both quantity *and* value between two locations — it decrements `inv_stock_balance` at the source, increments it at the destination, and moves the cost layer itself (`fn_consume_stock_cost_layers` at source → `fn_add_stock_cost_layer` at destination, at the exact same unit cost) so a transfer neither creates nor destroys value regardless of valuation method. Stock Adjustment corrects physical-vs-book mismatches (damage, found stock, write-offs) via an Increase/Decrease type, and — unlike almost every other document in this codebase — does **not** follow a draft→posted lifecycle. It posts on `pending_approval → approved`; rejecting a pending adjustment never touches stock at all. Both screens were recently extended (migrations 160 and 172 respectively) to support a genuine **either/or Warehouse-or-Branch picker** on every location field: a Branch pick is never resolved back to "the one warehouse it's linked to," it posts stock directly against the branch itself, with no warehouse required at all.

**Cycle Count** is meant to close the loop: record a physical count per product, compare it against system quantity, and — once approved — post the correction itself (it has its own real posting function, `fn_post_cycle_count`; it does not create a separate Stock Adjustment record, despite the config's own subtitle implying it "triggers" one). The backend for this is real and complete. However, **the screen is currently disabled in the sidebar** (`disabled: true` in `navigation.service.ts`), and independent of that flag, its "Existing Saved Records" grid is genuinely broken today: `mapToGridRows()` in the shared shell has no `case 'cycleCount'`, so it falls through to `default: return [];` and the grid renders permanently empty no matter how many counts are saved. This part of the task's framing is confirmed accurate. What is **not** commonly known, and is a material finding of this review: the exact same missing-case defect also affects **Stock Transfer, Stock Adjustment, and Opening Stock Entry** — none of the four appears anywhere in `mapToGridRows()`'s switch. Those three are *not* disabled in the sidebar, so users can reach them and save documents through them today, but their own "Existing Saved Records" grids are equally empty. See each screen's "Known gaps" section below for the precise line-level evidence.

## Part 2 — Manufacturing: narrative

The intended flow is **BOM Master → Production Planning → Material Issue for Production → Production Entry → Production Return / Material Consumption**: a BOM (`bomMasterConfig`, a *master* screen, not covered in this file) defines what raw materials and quantities a finished product needs; Production Planning schedules a production run against a BOM version and work center and shows the raw-material shortfall; Material Issue for Production is meant to draw those raw materials out of the warehouse against the plan; Production Entry is meant to record the output (produced/rejected/wastage quantities and cost) and increase finished-goods stock; and Production Return is meant to send unused issued material back to the warehouse. Material Consumption is a parallel, more general internal-usage document (department/project/recipe based, not necessarily tied to a production plan) for things like kitchen consumption or admin/maintenance usage. Internal Issue Slip, Shipment Entry and Gate Pass round out the group as three different flavors of "stock leaving the building without being sold": Internal Issue Slip is an employee/department hand-out with an optional return date; Shipment Entry is a dispatch-logistics record (vehicle, driver, LR number) meant to sit downstream of a Delivery Challan; Gate Pass is the physical security-gate authorization for any inward or outward movement, referencing a GRN or DC.

**None of this is actually wired to a backend.** All 8 screens in this group (Production Planning, Material Issue for Production, Production Entry, Production Return, Material Consumption, Internal Issue Slip, Shipment Entry, Gate Pass) are thin components that do nothing but set `config` on the shared `InventoryScreenShell` — there is no override, no custom save logic, nothing. Checked directly against the shell's `isApiWired()` allow-list, `loadApiRecords()` switch, and payload-building switch: **none of the 8 keys appear in any of the three.** There is no Postgres table, no stored procedure, and no C# method for any of them anywhere in the codebase (`InventoryTransactionsDataService.cs` and `InventoryDataService.cs` were both searched exhaustively — zero matches). All 8 are also marked `disabled: true` in `navigation.service.ts`, so this is at least honestly reflected in the sidebar, unlike Opening Inventory Balance (see below) which is unwired *and* has no sidebar entry to warn anyone off it. What each of these 8 screens does today, in practice: it shows hard-coded sample rows from `config.rows`, and clicking "Save" appends the entry to an in-memory `pendingRows` signal that is never persisted — refreshing the page loses everything. Interestingly, a handful of shell code paths (`segmentBarReferenceScreens`, a `shipmentEntry`-specific reference-reset branch) already list some of these screen keys as if wiring were mid-flight, but every one of those code paths is gated behind `isApiWired()`, which is false for all 8 — so that code is currently dead/unreachable for this group. This is exactly the "looks built but isn't fully wired" pattern flagged as a risk in this codebase's history, and it applies uniformly across the entire Manufacturing group, not to one or two screens.

## Opening Inventory Balance

**Business purpose:** Capture branch/warehouse-wise opening stock (quantity, rate, total value, batch/serial) before live inventory transactions begin. Intended as a one-time data-seeding screen.
**Predecessor / successor documents:** None. This screen is meant to run once, before any other transaction. In practice it has no relationship to anything else in the system because nothing reads or writes through it.
**Status lifecycle:** N/A — there is no save endpoint, so nothing is ever actually saved with a status.
**Key business rules:** The frontend fields use the same merged Warehouse/Branch picker (`INVENTORY_OPTIONS.locations`) as GRN/PI/DC/PR/SI, added when this screen was identified as having been missed by the original Full Warehouse/Branch Independence migration — but this is cosmetic parity only, since nothing behind the field does anything with the selection. No FIFO/LIFO/Weighted-Average cost-layer interaction exists, because there is no posting function at all.
**Accounting/GL impact:** None. No `sp_post_*` call exists or could exist — there is no save path to call it from.
**Frontend:** config key `openingInventoryBalanceConfig` (`inventory-screen.model.ts`, kind `master`) → component `src/app/inventory/Inventory_Masters/opening-inventory-balance/opening-inventory-balance.ts` (thin shell, no overrides).
**Backend — tables:** None.
**Backend — stored procedures:** None.
**Known gaps or flags:** This is a confirmed, deliberate finding, documented directly in the shared shell's own code comments (`inventory-screen-shell.ts`, around the `stockLocationScreenKeys` definition): *"Opening Inventory Balance is deliberately ABSENT — unlike its similarly-named sibling, it has no backend wiring at all (not in `isApiWired()`, no `buildPayload` case, no save endpoint): it is a static/mock master screen only, so there is no real POST to guard here **despite what its `outputImpact` copy claims**."* Its own config copy ("Opening balances seed stock ledger, valuation and availability reports") is therefore false as written. On top of that, this screen has **no entry at all in `navigation.service.ts`** — it isn't reachable from the sidebar under any group, only by direct URL (`/opening-inventory-balance` route exists in `inventory_routs.ts`). Recommendation for planning: either delete this screen (Opening Stock Entry is the real, wired equivalent) or repoint its route/nav at Opening Stock Entry and remove it, rather than leaving two near-identical, differently-functional screens in the codebase.

## Opening Stock Entry

**Business purpose:** Enter warehouse-wise opening stock (with a per-line Rate the user enters) before live inventory operations begin. This is the *real*, backend-wired version of "seed the ledger" — it genuinely increases `inv_stock_balance` and creates a real cost layer at the entered rate.
**Predecessor / successor documents:** None required as a predecessor (it is itself the starting point). Successor: any normal stock-consuming transaction (Sales Invoice, Delivery Challan, Stock Transfer, etc.) can draw against the balance and cost layer this creates.
**Status lifecycle:** `draft → posted` (standard two-state CHECK constraint on `inv_opening_stock_entries.status`). Posting is triggered by `status`/`post` flags on save, same idiom as GRN/PI.
**Key business rules:** Line qty is converted to base UOM via `fn_product_uom_base_qty` before touching stock. On post, `fn_post_opening_stock` increases `inv_stock_balance.qty_on_hand` (insert-if-not-found) and calls `fn_add_stock_cost_layer` at the item's own entered `rate` (not `cost_price` — this is the one screen in the group that establishes cost from a user-entered rate rather than approximating from an existing price). Serial-tracked products require `serial_numbers` matching qty exactly, inserted into `inv_serial_units` with `status='in_stock'`. **Frontend/backend mismatch (real gap):** the frontend field (`warehouse`, label "Warehouse / Branch") is one of the screens explicitly listed in the shell's `mergedLocationScreenKeys` set as having been retrofitted with the merged Warehouse/Branch picker ("this screen previously showed Branch and Warehouse as two separate mandatory fields, missed by the original migration"), and the table (`inv_opening_stock_entries`) has carried `branch_id`/`branch_name` columns since its original migration (143). But **`fn_post_opening_stock` itself was never updated** the way Stock Transfer (migration 160) and Stock Adjustment (migration 172) were — it still contains only `IF v_entry.warehouse_id IS NULL THEN RAISE EXCEPTION 'Opening Stock Entry requires a Warehouse.'`. A user who picks a branch-only location (no linked warehouse) on this screen will save successfully as a draft, but posting will fail with that exception. No later migration (checked all files referencing `opening_stock`/`inv_opening_stock`: only 139, 143, 157, 170) touches this function again.
**Accounting/GL impact:** None. No `sp_post_*` call in `SaveOpeningStockEntryAsync`.
**Frontend:** config key `openingStockEntryConfig` (`inventory-screen.model.ts`) → component `src/app/inventory/Inventory_Transactions/opening-stock-entry/opening-stock-entry.ts`.
**Backend — tables:**
- `inventory.inv_opening_stock_entries` — header: `entry_number`, `entry_date`, `segment_id`, `branch_id`/`branch_name`, `warehouse_id`/`warehouse_name`, `status` (`draft`/`posted`), `total_value`.
- `inventory.inv_opening_stock_entry_items` — lines: `product_id`, `variant_id`/`attribute_id`/`attribute_value`, `uom_id`, `qty`, `rate`, `amount`, `batch_no`/`serial_no`/`serial_numbers` (JSONB).
- `inventory.inv_stock_balance` — quantity increased on post.
- `inventory.inv_stock_cost_layers` — new layer added at the entered rate.
- `inventory.inv_serial_units` — new `in_stock` rows for serial-tracked products.
**Backend — stored procedures:**
- `inventory.sp_get_opening_stock_entries` — list with items, filtered by company/status/segment.
- `inventory.sp_save_opening_stock_entry` — insert/update header+lines, auto-generates `OSE-<segment>-<yy>-nnnnn`, calls the posting function when `post`/`status=posted` is supplied.
- `inventory.fn_post_opening_stock(p_entry_id, p_company_id)` — the actual stock/cost-layer/serial posting logic (warehouse-only, see gap above).
**Known gaps or flags:** (1) The `mapToGridRows()` empty-grid defect described under Cycle Count below applies identically here — `openingStockEntry` has no case in that switch, so its "Existing Saved Records" grid is empty in the live app today even though the screen is fully wired and not disabled in the sidebar. (2) The warehouse-only posting gap described above (branch-only pick will fail at post time despite the merged picker suggesting it's supported).

## Stock Transfer

**Business purpose:** Move stock (quantity and value) between two locations — branch-to-branch, warehouse-to-warehouse, or mixed — without a sale or purchase.
**Predecessor / successor documents:** No formal predecessor document reference (the From location simply needs sufficient stock). No formal successor reference either — Shipment Entry/Gate Pass conceptually could accompany the physical movement, but there is no code-level link between them (those two screens have no backend at all, see Manufacturing group).
**Status lifecycle:** `draft → posted`, standard two-state CHECK constraint on `inv_stock_transfers.status`. Posting a draft is a distinct user action from the "Existing Saved Records" grid (`postStockTransferRecordByRow()` → re-loads the record into the form → re-saves with `status='posted'`).
**Key business rules:** Both From and To fields are merged Warehouse/Branch pickers (`resolveMergedLocation()` on the frontend); each side independently resolves to either a `*_warehouse_id` or a `*_branch_id`, never both, and a branch-only pick is fully valid with no linked warehouse required. `fn_post_stock_transfer` (last redefined in migration 160) requires a location (warehouse OR branch) on **both** sides, and rejects if the resolved source and destination are the same location. It moves quantity via `fn_upsert_stock_balance` (branch-aware, refuses rather than clamps on insufficient stock — a correctness fix from migration 156, which replaced an earlier version that clamped at zero and could silently net-create stock). It moves *value* by consuming the source's cost layer(s) via `fn_consume_stock_cost_layers` and re-adding the exact same computed unit cost at the destination via `fn_add_stock_cost_layer` — a transfer never creates or destroys value regardless of the product's FIFO/LIFO/Weighted-Average setting. Serial-tracked products have their `inv_serial_units.warehouse_id` physically relocated (the only posting function in this codebase that moves a serial between locations rather than just changing its status). The Stock Ledger Report (migration 156) was extended to include Stock Transfer as two derived movement lines (an outward line at From, an inward line at To) with `rate` left NULL so the transfer doesn't disturb the report's running value.
**Accounting/GL impact:** **Yes — this is the one screen in the Stock Movement group with real, newly-added double-entry accounting** (migration `174_stock_transfer_accounting_posting.sql`, procedure `accounts.sp_post_stock_transfer`, called from `InventoryTransactionsDataService.SaveStockTransferAsync` immediately after `inventory.sp_save_stock_transfer` returns `status='posted'`). It posts exactly 4 ledger rows per transfer, using the **real cost** already computed by the valuation engine (`SUM(received_qty * unit_cost)` from `inv_stock_cost_layers` where `source_doc_type='stock_transfer' AND source_doc_id=<transfer id>` — never recomputed):
  - Source location's books: **Dr "Inter Branch - `<destination name>`"** / **Cr "Stock Transfer Out"**
  - Destination location's books: **Dr "Stock Transfer In"** / **Cr "Inter Branch - `<source name>`"**
  Works uniformly for branch→branch, warehouse→warehouse, and mixed transfers via the new `location_branch_id`/`location_warehouse_id` columns added to `accounts.tbl_trans_total_transactions` by this same migration (kept deliberately separate from the pre-existing, unrelated `branch_id` column, which FKs to a legacy chit-fund-era branch table). "Inter Branch - `<location>`" sub-ledgers are created on demand under a parent "Inter Branch" account by `accounts.fn_ensure_location_subledger()`, mirroring the existing `fn_ensure_party_subledger()` pattern. Posting is idempotent (checked by `transaction_no` + `accountname='Stock Transfer Out'`) and only fires when `sp_save_stock_transfer` actually transitions status to `'posted'` — never on a draft save, and skipped entirely for a zero-cost transfer.
**Frontend:** config key `stockTransferConfig` (`inventory-screen.model.ts`) → component `src/app/inventory/Inventory_Transactions/stock-transfer/stock-transfer.ts`.
**Backend — tables:**
- `inventory.inv_stock_transfers` — header: `transfer_number`, `transfer_date`, `segment_id`, `from_branch_id`/`from_warehouse_id`, `to_branch_id`/`to_warehouse_id`, `status` (`draft`/`posted`), `total_qty`.
- `inventory.inv_stock_transfer_items` — lines: product/variant/attribute/UOM, `qty`, `batch_no`/`serial_no`/`serial_numbers`.
- `inventory.inv_stock_balance`, `inventory.inv_stock_cost_layers`, `inventory.inv_serial_units` — moved on post.
- `accounts.tbl_trans_total_transactions` — 4 new debit/credit rows per posted transfer (new columns `location_branch_id`, `location_warehouse_id`).
- `accounts.tbl_mst_account` — seeded with "Stock Transfer Out", "Stock Transfer In", "Inter Branch" (parent) accounts, plus on-demand "Inter Branch - `<location>`" sub-ledgers.
**Backend — stored procedures:**
- `inventory.sp_get_stock_transfers` / `inventory.sp_save_stock_transfer` — CRUD + auto-numbering (`ST-<segment>-<yy>-nnnnn`).
- `inventory.fn_post_stock_transfer(p_transfer_id, p_company_id)` — quantity/value/serial movement (migration 160's version is live).
- `accounts.sp_post_stock_transfer(p_data, o_result)` — the 4-row GL posting described above.
- `accounts.fn_ensure_location_subledger(p_location_type, p_location_id, p_location_name)` — creates/returns the "Inter Branch - `<name>`" sub-ledger account.
**Known gaps or flags:** The "Existing Saved Records" grid is empty in the live app. `mapToGridRows()` in `inventory-screen-shell.ts` has cases for every master screen and for every Procure-to-Pay/Order-to-Cash transaction screen (`purchaseRequisition` through `creditNote`), but **no `case 'stockTransfer':`** — confirmed by grep across the full switch body (lines ~19589–19850). It falls to `default: return [];`. Since `isApiWired()` is true for this key, `liveRows()` calls `mapToGridRows()` unconditionally, so the grid renders zero rows regardless of how many transfers exist in `savedRecordObjects()`. This is the identical defect commonly attributed only to Cycle Count, and it is live and unflagged (no `disabled: true` in the sidebar) for this screen today.

## Stock Adjustment

**Business purpose:** Correct physical-vs-book stock discrepancies (damage, found stock, write-offs, shrinkage) via an Increase/Decrease adjustment with an approval step, rather than a free-form stock edit.
**Predecessor / successor documents:** No formal system link, but conceptually often follows a Cycle Count variance — there is, however, **no actual document reference field or FK** between Cycle Count and Stock Adjustment; Cycle Count posts its own variance directly via its own `fn_post_cycle_count` rather than generating a Stock Adjustment record. No successor document.
**Status lifecycle:** **Confirmed as documented in the brief: `pending_approval → approved`, not `draft → posted`.** `inv_stock_adjustments.status` CHECK constraint is `('pending_approval', 'approved', 'rejected')`. `sp_save_stock_adjustment` calls `fn_post_stock_adjustment` only when the incoming status is `'approved'` and the previous status wasn't already `'approved'`. Rejecting a pending adjustment (`status='rejected'`) never touches stock. Once a record leaves `pending_approval` (approved or rejected), `sp_save_stock_adjustment` explicitly refuses further edits: `RAISE EXCEPTION 'This Stock Adjustment has already been % and can no longer be edited.'`. This is a genuinely different lifecycle from every draft/posted screen in the module, exactly as flagged.
**Key business rules:** Increase and Decrease are handled asymmetrically. **Increase**: adds stock via `fn_upsert_stock_balance` and creates a new cost layer at the product's *current* `cost_price` (there's no purchase rate on an adjustment, so this mirrors the same approximation `fn_post_sales_return_stock` uses for goods coming back); serial-tracked products get brand-new `inv_serial_units` rows. **Decrease**: consumes stock and cost layers like any other outward movement; serial-tracked units transition to a dedicated terminal status `'written_off'` (the `inv_serial_units_status_check` CHECK constraint was widened in migration 142 specifically to add this — reusing `'sold'` would have been semantically wrong). **Full Warehouse/Branch Independence:** as of migration 172 ("user request: 'in stock adjustment should add even branches too'"), the single location field on this screen supports a merged Warehouse-or-Branch picker exactly like Stock Transfer's two sides — a branch-only pick is fully valid with no linked warehouse, and `fn_post_stock_adjustment`'s guard was changed from `IF v_adj.warehouse_id IS NULL` to `IF v_adj.warehouse_id IS NULL AND v_adj.branch_id IS NULL`. This was the *last* screen in the module still showing a Warehouse-only picker before this migration. `fn_add_stock_cost_layer`/`fn_consume_stock_cost_layers` calls were updated to pass the branch id through (trailing parameter, appended rather than inserted mid-list to avoid breaking the other 10 live positional callers of those two functions). A "Reason" is a plain free-text field with **no dedicated Reason master**, and "Approval" is the generic `status` dropdown with **no real multi-step approval routing** — the frontend's own `dependsOn` array was corrected in a recent pass to stop overclaiming these as "Ready".
**Accounting/GL impact:** **None.** Checked directly: `InventoryTransactionsDataService.SaveStockAdjustmentAsync` calls only `inventory.sp_save_stock_adjustment` — there is no `accounts.sp_post_*` call anywhere in its save path, unlike Stock Transfer.
**Frontend:** config key `stockAdjustmentConfig` (`inventory-screen.model.ts`) → component `src/app/inventory/Inventory_Transactions/stock-adjustment/stock-adjustment.ts`.
**Backend — tables:**
- `inventory.inv_stock_adjustments` — header: `adjustment_number`, `adjustment_date`, `segment_id`, `branch_id`/`branch_name`, `warehouse_id`/`warehouse_name`, `adjustment_type` (`Increase`/`Decrease`), `reason` (free text), `status` (`pending_approval`/`approved`/`rejected`), `approved_by`/`approved_at`.
- `inventory.inv_stock_adjustment_items` — lines: product/variant/attribute/UOM, `qty`, `batch_no`/`serial_no`/`serial_numbers`.
- `inventory.inv_stock_balance`, `inventory.inv_stock_cost_layers`, `inventory.inv_serial_units` — updated on approval.
**Backend — stored procedures:**
- `inventory.sp_get_stock_adjustments` / `inventory.sp_save_stock_adjustment` — CRUD + auto-numbering (`SA-<segment>-<yy>-nnnnn`), approval-gate + edit-lock logic described above.
- `inventory.fn_post_stock_adjustment(p_adjustment_id, p_company_id)` — the Increase/Decrease stock and cost-layer logic (migration 172's branch-aware version is live).
**Known gaps or flags:** Same empty-grid defect as Stock Transfer and Opening Stock Entry: `mapToGridRows()` has no `case 'stockAdjustment':`, so this screen's "Existing Saved Records" grid is also empty in the live app today, despite the screen being fully wired, live in the sidebar, and having a real, correct approval-gated posting function underneath it. Separately, the "Reason" and "Approval" `dependsOn` overclaims noted above are already self-corrected in the current config copy (worth calling out as an example of this codebase's habit of overclaiming "Ready" that has since been caught and fixed here, even though the grid-rendering bug next to it was not).

## Cycle Count

**Business purpose:** Record a physical stock count per product against a warehouse, compare it to the system quantity, and — on approval — post the variance directly to stock.
**Predecessor / successor documents:** No formal predecessor. No successor document is created — despite the screen's own subtitle/`outputImpact` text ("Physical count variance triggers stock adjustment for approval"), approving a Cycle Count does **not** create a Stock Adjustment record; it posts the correction itself via its own dedicated function.
**Status lifecycle:** `pending_approval → approved` / `rejected` — the same model as Stock Adjustment, and for the same reason (a count sheet's variance only becomes a real stock correction once someone signs off on it). `sp_save_cycle_count` refuses further edits once a record leaves `pending_approval`, identically to Stock Adjustment.
**Key business rules:** Direction is **per line**, not per document — one count sheet can have some lines short and others over; `fn_post_cycle_count` loops items individually rather than applying one adjustment type to the whole document (this is the one structural difference from Stock Adjustment). The variance actually posted is **recomputed live at approval time** from the current `inv_stock_balance.qty_on_hand`, not read back from whatever `system_qty` the line stored at count-entry time — this makes the count self-correcting against anything that moved stock between counting and approval (a sale, another adjustment, etc.); the line's stored `system_qty` is purely an audit-trail snapshot of what the sheet showed at count time. A positive live variance adds stock and a new cost layer at the product's current `cost_price`; a negative live variance consumes stock/cost layers via the standard FIFO/LIFO/Weighted-Average consumption function. **No Full Warehouse/Branch Independence here:** unlike Stock Transfer and Stock Adjustment, Cycle Count's `warehouse` field and `fn_post_cycle_count` were never extended for branch support — it is warehouse-only (`IF v_cnt.warehouse_id IS NULL THEN RAISE EXCEPTION 'Cycle Count requires a Warehouse.'`), and no later migration touches it.
**Accounting/GL impact:** None. `SaveCycleCountAsync` calls only `inventory.sp_save_cycle_count`; no `accounts.sp_post_*` call exists.
**Frontend:** config key `cycleCountConfig` (`inventory-screen.model.ts`) → component `src/app/inventory/Inventory_Transactions/cycle-count/cycle-count.ts`.
**Backend — tables:**
- `inventory.inv_cycle_counts` — header: `verification_number`, `verification_date`, `segment_id`, `warehouse_id`/`warehouse_name`, `verified_by_name`, `product_category_id`, `status` (`pending_approval`/`approved`/`rejected`), `total_items`/`variance_items`, `approved_by`/`approved_at`.
- `inventory.inv_cycle_count_items` — lines: product/variant/attribute/UOM, `system_qty` (snapshot), `physical_qty`, `variance_qty` (as computed at *save* time — the value actually posted is recomputed live, see above), `reason`.
- `inventory.inv_stock_balance`, `inventory.inv_stock_cost_layers` — updated on approval.
**Backend — stored procedures:**
- `inventory.sp_get_cycle_counts` / `inventory.sp_save_cycle_count` — CRUD + auto-numbering (`CC-<segment>-<yy>-nnnnn`), same approval-gate + edit-lock pattern as Stock Adjustment.
- `inventory.fn_post_cycle_count(p_count_id, p_company_id)` — per-line, live-recomputed variance posting described above.
**Known gaps or flags:** **Confirmed, current, and exactly as described in the brief.** Two independent, compounding problems exist today:
  1. This screen carries `disabled: true` in `navigation.service.ts`'s Inventory group, so it is not reachable from the sidebar at all.
  2. Its "Existing Saved Records" grid would be empty even if it were re-enabled: `mapToGridRows()` has no `case 'cycleCount':`, falling to `default: return [];`, identically to Stock Transfer, Stock Adjustment and Opening Stock Entry (see those sections — **this is a shared root cause across all four Stock Movement transaction screens, not a Cycle Count–specific defect**, even though Cycle Count is the only one of the four currently hidden behind the sidebar flag). The backend underneath Cycle Count is otherwise complete and correct (auto-numbering, approval gating, live-recomputed per-line variance posting, edit-lock after decision) — this is purely a frontend rendering gap in the shared shell, fixable by adding one `case` block per screen key to `mapToGridRows()` that maps each screen's known response fields (`verification_number`, `verification_date`, `warehouse_name`, `verified_by_name`, item/variance counts, `status`) to `config.columns`' order, the same way every other transaction screen already does.

## Production Planning

**Business purpose:** Plan a production run — finished product, planned quantity, BOM version, work center, production warehouse — and show the raw-material requirement (pulled conceptually from the BOM) against currently available quantity, flagging any shortage.
**Predecessor / successor documents:** Conceptually follows BOM Master (a master-data screen, out of scope here). Intended successor: Material Issue for Production (its `productionRef` field is meant to reference this plan). In the live code, none of this linkage is real — the `productionRef`/`bomVersion`/`workCenter` select fields are either static hard-coded option arrays or empty (`options: []`), not fetched from any saved BOM or plan record.
**Status lifecycle:** None. There is no `status` CHECK constraint, no draft/posted or approval state machine, because there is no table to hold one. The sample "In Progress"/"Completed" values in `config.rows` are static demo text.
**Key business rules:** None enforced. The "Raw Material Requirements (From BOM)" line grid shown on save is static sample data (`config.lineRows`), not a real BOM explosion — no code path reads `bomMasterConfig`'s raw materials and multiplies by planned quantity.
